# 公开发布检查清单

## 当前版本的技术边界

发布版本不带已保存项目、业务数据文件、样例本体、预制业务规则或个人模型配置。模型服务商、地址、模型名和密钥初始为空。代码中保留的公开协议标识、默认端口、输出预算和参数定义属于运行所需的公开程序设置。

`tests/` 与 `check.mjs` 会在测试时构造虚构数据；它们不是客户数据，也不会随首次启动加载。完全删除测试代码中的所有虚构值会使测试失效。发布包不包含测试运行产物。

## 不应公开的内容

| 内容 | 处理方式 |
| --- | --- |
| 真实合同、凭证、业务表、个人信息、上传附件 | 留在本机运行目录；对外演示重新构造虚构材料 |
| API Key、Token、私钥、证书密码、数据库口令 | 不入仓库；若曾暴露先撤销或轮换 |
| 内网地址、生产连接串、账号、私有部署参数 | 删除真实值；文档只保留公开参数定义 |
| 客户名称、内部制度、保密规则、咨询交付文档 | 依据保密约定和授权决定是否可公开，不能只做改名处理 |
| 无权再许可的公司或客户项目代码、复制的第三方组件 | 获得授权或替换；保留必须的原始版权和许可 |
| 无授权商标、图片、字体、商业素材、模型权重 | 删除或按相应许可使用，不能仅以项目许可证覆盖 |
| 历史提交、日志、备份、截图、导出 ZIP 中的敏感内容 | 独立检查；不要把原工作目录或旧 `.git` 整体上传 |

## 发布步骤

1. 确认有权将代码及通用提示词以 Apache-2.0 许可公开。若源于公司或客户项目，检查合同、职务成果归属和保密义务；代码改名不能代替授权。
2. 运行 `npm test`、`npm run check`、`npm run release:check`。
3. 运行 `npm run release:zip`，使用生成的源码包。打包脚本采用文件白名单，避免把本机运行资料带入。
4. 在新的空目录中解压，检查文件清单及 `SHA256SUMS`；不要复制旧项目的 `.git`。
5. 建立仓库后，检查实际暂存内容。启用 GitHub 可用的 secret scanning / push protection，并按仓库策略保护主分支。
6. 发布截图、录屏、Issue 和使用案例时继续使用虚构材料，检查浏览器地址栏、控制台和密钥输入框。

现有扫描只是在已知规则下未发现命中，不是“绝无敏感信息”或“权属清白”的证明。原压缩包没有历史提交，因此无法据此审查旧开发仓库的提交历史。

## GitHub 与运行托管

GitHub 可以承载源码。此项目需要 Node.js 服务端，GitHub Pages 的静态托管不能运行完整工作台；离线查看器是独立的静态页面。将完整服务公开部署，需要另行设计认证、权限、数据隔离、TLS 和运行环境保护。

参考：[Apache-2.0 正文](https://www.apache.org/licenses/LICENSE-2.0)、[GitHub 仓库许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)、[敏感数据清理](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。
